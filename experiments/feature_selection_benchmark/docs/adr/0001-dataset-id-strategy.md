# ADR 0001 — Стратегия идентификации `dataset_id`

- **Статус:** Accepted
- **Дата:** 2026-05-17
- **Эпик:** E-002 [Critical] (Research) Идентификация записей глобального лидерборда
- **Закрывает:** OVERVIEW §9 Q1 (часть про идентификацию записи)

## Контекст

Глобальный лидерборд (таблица `leaderboard`) и таблица `runs` сравнивают
результаты отбора признаков **между прогонами**. Чтобы сравнение было
осмысленным, нужно знать, что два прогона работали «с тем же датасетом». Эту
идентичность кодирует поле `dataset_id` (`runs.dataset_id`,
`leaderboard.dataset_id` — оба `TEXT NOT NULL`, ARCHITECTURE §5).

Каркас E-001 зафиксировал, что `storage/leaderboard.py` принимает `dataset_id`
как **готовую строку**; механизм её генерации был отложен как открытый вопрос
OQ-2 в этот эпик.

Ограничения, формирующие решение:

- `Dataset.data` (сырые данные пользователя) **никогда не пишется на диск**
  (ARCHITECTURE §5, §7) — значит, в основу id нельзя класть то, что нельзя
  безопасно вычислить из данных в RAM, но сам результат должен быть пригоден
  для записи в SQLite.
- Датасеты в проекте не каталогизируются и не версионируются (NEVER §3) —
  внешнего реестра датасетов, из которого можно взять id, нет.
- Воспроизводимость (критерий К2): при одинаковых входах id обязан совпадать
  от запуска к запуску и между процессами.

## Рассмотренные варианты

### A — content-hash (хэш содержимого данных)

Хэшировать значения всего датасета.

- `+` полностью автоматически; разные данные → разный id.
- `−` дорого на больших датасетах (нет жёсткого лимита размера — К4).
- `−` хрупко: id зависит от порядка строк, dtype, индекса.
- `−` «тот же датасет + одна новая строка» → другой id, что рвёт сравнимость
  записей лидерборда при обычном дополнении данных.

### B — пользовательское имя

`dataset_id` = имя, заданное пользователем.

- `+` дёшево, человекочитаемо, стабильно при правках данных.
- `−` полностью полагается на дисциплину пользователя; два **разных** датасета
  под одним именем молча сольются в одну запись лидерборда без сигнала.

### C — имя + структурный fingerprint *(выбрано)*

`dataset_id = "{name}::{fingerprint}"`, где `fingerprint` — хэш **схемы**
датасета (имена колонок + их dtype), а не значений.

- `+` человекочитаемо (имя в префиксе).
- `+` дёшево — хэшируется только метаданные схемы, не данные.
- `+` ловит главный footgun варианта B: одно имя на структурно разных датасетах
  даёт разный id.
- `+` не нарушает «данные не на диск» — в хэш идут только имена колонок и dtype.
- `+` стабильно при добавлении/удалении строк (число строк в хэш не входит).
- `−` не различает датасеты с одинаковой схемой, но разными значениями
  (см. Known Limitations).

## Решение

Принят вариант **C**.

### Формат `dataset_id`

```
dataset_id := "{name}::{fingerprint}"
fingerprint := first 12 hex chars of SHA-256(schema_string)
schema_string := "|".join("{column}:{dtype.name}" for column in data.columns)
```

- Колонки берутся в порядке `data.columns`; включают и признаки, и целевую
  колонку (бенчмарк на той же таблице, но другом target — другая задача).
- В `schema_string` **не входят** число строк и значения ячеек.
- dtype канонизируется через `numpy`/`pandas` dtype `.name` (`int64`,
  `float64`, `object`, `category`, `Int64`, …) — стабильно между версиями
  pandas.
- Хэш — только `hashlib.sha256`. Встроенный `hash()` запрещён: он солится по
  процессу и дал бы разный id между запусками.
- Длина fingerprint — 12 hex-символов (48 бит): компактно и читаемо при
  пренебрежимой вероятности случайной коллизии на человеко-масштабном числе
  датасетов.

### Реализация

Функция реализована в эпике E-002 (подзадача E-002.1):

```python
# feature_selection_benchmark/storage/dataset_id.py
def compute_dataset_id(name: str, data: pd.DataFrame) -> str: ...
```

Функция размещена в слое `storage` и принимает примитивы (`str`,
`pd.DataFrame`), а **не** объект `Dataset`: слоистая архитектура запрещает
`storage` импортировать `api.Dataset` (восходящая зависимость). Вызывает
функцию слой API сверху вниз.

`name` обязателен и непуст — иначе `ValueError`.

## Спецификация для downstream-эпиков

### E-004 (API-слой: точка входа и `Dataset`) — **требуется правка контракта**

Стратегия C нуждается во входе `name`, которого в текущем контракте нет
(`Dataset` не имеет поля имени, `run_benchmark` — параметра имени). E-004 —
владелец этого контракта; E-002 контракт не правит, а специфицирует:

- **Рекомендация:** добавить параметр `dataset_name: str` в `run_benchmark(...)`
  (а не поле в `Dataset`). Обоснование: `dataset_name` — характеристика
  *прогона/задачи сравнения*, а не самих данных; `Dataset` остаётся чистым
  контейнером данных. Параметр размещать рядом с `task`.
- **Поведение при отсутствии имени (OQ-2):** рекомендуется сделать
  `dataset_name` обязательным (без значения по умолчанию) — глобальный
  лидерборд без осмысленного имени бесполезен, а молчаливый дефолт
  (`"unnamed"`) провоцирует коллизии. Финальное решение — за E-004.
- `run_benchmark` вычисляет `dataset_id` через `compute_dataset_id(dataset_name,
  dataset.data)` и передаёт готовую строку в слой storage.

### E-007 (Хранилище и лидерборды) — потребление

- `storage/leaderboard.py` (`update`, `read_leaderboard`) уже принимает
  `dataset_id: str` — менять сигнатуры не нужно.
- E-007 импортирует и вызывает `compute_dataset_id` либо получает уже
  вычисленный `dataset_id` от слоя API.
- Запись в `runs.dataset_id` и `leaderboard.dataset_id` — этой же строкой.

## Последствия

### Положительные

- `dataset_id` человекочитаем, дёшев, воспроизводим между процессами.
- Структурно разные датасеты под одним именем не сливаются в лидерборде.
- Слой storage не зависит от слоя API.

### Known Limitations

- **Коллизия по значениям (риск R-4).** Два разных датасета с одинаковым
  именем и одинаковой схемой (те же колонки и dtype, но другие значения)
  получают один `dataset_id` и сливаются в одну запись лидерборда. Это
  осознанный компромисс варианта C; в v1 не устраняется. Обходной путь для
  пользователя — задавать различающиеся `dataset_name`. При необходимости в
  будущем добавляется опциональный сегмент content-hash.
- **Чувствительность к именованию колонок.** Переименование колонки или смена
  её dtype меняет `dataset_id` — это намеренно (другая схема = другой датасет),
  но означает, что косметические правки схемы создают новую запись лидерборда.
