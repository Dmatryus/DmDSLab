# ADR 0002 — Стратегия подбора гиперпараметров FS-методов

- **Статус:** Accepted
- **Дата:** 2026-05-17
- **Эпик:** E-003 [Critical] (Research) Стратегия подбора гиперпараметров FS-методов
- **Закрывает:** OVERVIEW §9 Q2

## Контекст

Перед прогоном FS-метода через кросс-валидацию бенчмарк подбирает его
гиперпараметры (порог дисперсии, число отбираемых признаков, сила
регуляризации и т.п.). Открытый вопрос Q2 (OVERVIEW §9): какой стратегией
работает этот подбор.

Что зафиксировано каркасом E-001:

- `core/tuning.py` — `tune_hyperparams(method, dataset, n_trials=20,
  random_seed) -> dict` (заглушка). Шаг подбора уже встроен в архитектуру.
- `run_benchmark(... n_trials: int = 20 ...)` — параметр бюджета подбора в
  публичном API. Имя `n_trials` — терминология Optuna
  (`study.optimize(n_trials=...)`): расчёт на Optuna заложен изначально.
- ARCHITECTURE §3 Data Flow: для каждого метода `tune_hyperparams(...)` →
  `best_params` → `run_cv(method, dataset, best_params)`.
- `MethodInfo.hyperparameters: dict[str, Any]` — «имя → значение по
  умолчанию / описание».

Ограничения, формирующие решение:

- Замысел продукта — автоматический бенчмарк (OVERVIEW §2): ручная настройка
  гиперпараметров пользователем противоречит цели.
- Воспроизводимость (критерий К2): при одинаковых данных, задаче и
  `random_seed` лидерборд обязан совпадать с допуском 1e-6.
- Нет жёстких лимитов на размер датасета (К4) — стоимость подбора ограничена
  железом пользователя.

## Рассмотренные варианты

### A — фиксированные defaults из гида

Каждый метод гоняется один раз с задокументированными дефолтами.

- `+` дёшево (1 CV на метод), полностью воспроизводимо, просто.
- `−` `n_trials` становится мёртвым параметром; методы сравниваются не в
  лучшей форме — метод, чувствительный к гиперпараметрам, несправедливо
  проигрывает.

### B — встроенный random search

Per-method: сэмплировать `n_trials` случайных конфигов, CV-оценить, взять
лучший.

- `+` методы сравниваются близко к пику; `n_trials` уже в API.
- `−` случайный поиск не учится на предыдущих trials — расходует бюджет
  менее эффективно, чем направленный поиск.

### C — grid search

Исчерпывающий перебор сетки.

- `−` размер сетки фиксирован — не ложится на бюджет `n_trials`; комбинаторный
  взрыв. Вытесняется направленным поиском.

### D — ручная передача параметров

Пользователь задаёт гиперпараметры каждого метода.

- `−` противоречит замыслу автоматического бенчмарка. Допустимо лишь как
  необязательный override поверх основной стратегии, не как сама стратегия.

### E — Optuna TPE + fallback на defaults *(выбрано)*

Встроенный подбор через Optuna с сэмплером TPE
(Tree-structured Parzen Estimator); бюджет = `n_trials`. При `n_trials = 0` —
fallback на фиксированные дефолты без запуска поиска.

- `+` TPE учится на результатах предыдущих trials — эффективнее случайного
  поиска при том же бюджете.
- `+` полностью согласован с уже зафиксированным контрактом (`n_trials`,
  `tune_hyperparams`); имя `n_trials` — прямая терминология Optuna.
- `+` вбирает в себя варианты A (`n_trials=0`) и B (направленный поиск вместо
  случайного); ручной override (D) ложится сверху.
- `−` сложнее остальных; сохраняется оптимистичное смещение оценки
  (см. Known Limitations).

## Решение

Принят вариант **E**.

### Стратегия подбора

- Подбор гиперпараметров каждого FS-метода — через Optuna со сэмплером
  `TPESampler`.
- Бюджет — параметр `n_trials` из `run_benchmark` / `tune_hyperparams`.
- При `n_trials = 0` study не создаётся: метод запускается на фиксированных
  дефолтах (дешёвый режим без поиска). Дефолт `n_trials = 20` → по умолчанию
  поиск выполняется.
- Ручная передача гиперпараметров пользователем — возможный будущий override
  поверх стратегии; в скоуп v1 не входит.

### Поведение `tune_hyperparams` (спецификация для E-006)

```
tune_hyperparams(method, dataset, n_trials, random_seed) -> dict:
    если n_trials == 0:
        вернуть дефолтные гиперпараметры метода (без study)
    study = optuna.create_study(
        direction="maximize",
        sampler=optuna.samplers.TPESampler(seed=random_seed),
    )
    objective(trial):
        params = <сэмплировать из пространства поиска метода через trial>
        selected = method.fit_select(X_train, y_train, **params)
        вернуть CV-оценку набора selected
    study.optimize(objective, n_trials=n_trials)
    вернуть study.best_params
```

- `direction="maximize"` — все метрики качества проекта «больше = лучше»
  (для метрик-ошибок оркестратор оценки инвертирует).
- Если у метода нет настраиваемых гиперпараметров — подбор пропускается,
  возвращается пустой dict.

### Объявление пространства поиска (спецификация для E-005)

Каждый FS-метод декларирует **declarative** пространство поиска — обычные
данные, без зависимости от Optuna (слой `methods/` не импортирует `optuna`;
трансляцию в `trial.suggest_*` делает только `core/tuning.py`).

Рекомендуемая форма — по гиперпараметру дескриптор:

```
{
    "kind": "int" | "float" | "categorical",
    "low": ...,         # для int/float
    "high": ...,        # для int/float
    "log": bool,        # для int/float — логарифмическая шкала
    "choices": [...],   # для categorical
    "default": ...,     # значение для режима n_trials=0
}
```

`core/tuning.py` транслирует `kind` в соответствующий вызов
`trial.suggest_int` / `suggest_float` / `suggest_categorical`.

Точная форма контракта (расширение `MethodInfo.hyperparameters` против
отдельного типа `SearchSpace` в `methods/base.py`) — открытый вопрос OQ-1,
финализируется эпиком E-005 при реализации методов.

### Дефолтные значения

Дефолт каждого гиперпараметра (поле `default`, режим `n_trials=0`) берётся из
`docs/feature_selection_guide.md`, если гид даёт рекомендацию для метода;
иначе — дефолт нижележащей библиотеки (`scikit-learn`, `catboost` и др.).
Конкретные значения задаются при реализации методов в эпике E-005.

### Зависимость

`optuna` добавляется в **core-зависимости** `pyproject.toml` (стек
ARCHITECTURE §1 ранее её не содержал). Optuna — чистый Python, без тяжёлой
C++-сборки (в отличие от `catboost` / `shap`), поэтому в core, а не в
опциональный extra. Добавление выполняет эпик E-006 (оператор `~=`).

### Воспроизводимость (К2)

`TPESampler` сидируется `random_seed`: при одинаковых `random_seed`, данных и
задаче последовательность trials и `best_params` детерминированы → лидерборд
воспроизводим с допуском 1e-6. При `random_seed = None` подбор
невоспроизводим — это согласуется с общей семантикой `random_seed` в проекте
(нефиксированный прогон).

## Спецификация для downstream-эпиков

### E-005 (Реестр методов и FS-методы)

- Каждый FS-метод декларирует declarative-пространство поиска своих
  гиперпараметров (форма выше) и дефолтные значения.
- Финализировать форму контракта (`MethodInfo.hyperparameters` vs новый тип
  `SearchSpace`) — OQ-1.
- Слой `methods/` не импортирует `optuna`.

### E-006 (Ядро оркестрации)

- Реализует `tune_hyperparams` по спецификации выше (Optuna study,
  `TPESampler(seed=random_seed)`, objective = CV-оценка набора признаков).
- Добавляет `optuna~=<версия>` в core-зависимости `pyproject.toml`.
- Транслирует declarative-пространство поиска метода в вызовы
  `trial.suggest_*`.

## Последствия

### Положительные

- Подбор направленный (TPE) — эффективнее случайного при равном бюджете.
- Решение согласовано с уже существующим контрактом каркаса — правок
  публичного API `run_benchmark` не требуется.
- Режим `n_trials=0` сохраняет дешёвый воспроизводимый прогон на дефолтах.
- Слой `methods/` остаётся независимым от Optuna.

### Known Limitations

- **Оптимистичное смещение оценки.** Гиперпараметры метода подбираются по той
  же кросс-валидации, по которой метод затем оценивается в лидерборде —
  итоговая `cv_score` смещена оптимистично. Для v1 это принимается и
  документируется: все методы обработаны единообразно, поэтому *ранжирование*
  методов остаётся сопоставимым, хотя абсолютные значениях `cv_score` —
  завышены. Возможное будущее улучшение — nested CV (внешний фолд для оценки,
  внутренний — для подбора), отклонено для v1 как кратно более дорогое.
- **Стоимость.** Подбор умножает стоимость прогона примерно на `n_trials`.
  Жёсткого лимита нет (К4); пользователь управляет балансом через `n_trials`
  (вплоть до `0` — режим дефолтов).
